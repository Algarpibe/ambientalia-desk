# CI / lock-in — Fase C — Implementation Plan

> REQUIRED SUB-SKILL: subagent-driven-development.

**Goal:** GitHub Actions CI que corre typecheck+lint+test+build en cada PR (y en push a main), + tests de los guardas admin/SSRF, para que branch protection bloquee regresiones antes de llegar a `main`/prod.

**Spec/decisión:** Gate real — ramas + PR + branch protection (confirmado por el usuario). EasyPanel despliega en push a `main`; con branch protection, `main` solo recibe merges con CI verde → deploy blindado.

**Stack CI:** Node 22 (match prod), npm workspaces, vitest+pg-mem (no necesita BD real).

---

## Task 1: Workflow de CI + test SSRF (F5-01, F5-03)

**Files:** Create `.github/workflows/ci.yml`; Modify `apps/desk/server/app.test.ts`.

- [ ] **Step 1: `.github/workflows/ci.yml`:**
```yaml
name: CI
on:
  pull_request:
    branches: [main]
  push:
    branches: [main]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
          cache: 'npm'
      - run: npm ci
      - run: npm run typecheck
      - run: npm run lint
      - run: npm test
      - run: npm run build
```

- [ ] **Step 2: Test SSRF (F5-03)** — leer primero el helper real de `app.test.ts` (`appWith()` + `userCookie`/`adminCookie`). Añadir:
```ts
it('SSRF guard: ruta de adjunto inválida → 400', async () => {
  const { app } = appWith()
  const op = await userCookie([])
  const res = await request(app).get('/api/attachment?path=/evil/arbitrary').set('Cookie', op)
  expect(res.status).toBe(400)
})
```
(La regex de `/api/attachment` solo acepta `^/tickets/\d+/(comments|threads)/\d+/attachments/\d+/content$`; una ruta arbitraria → 400 sin llamar a Zoho. Ajustar `appWith()`/`userCookie` al patrón exacto del archivo.)

- [ ] **Step 3:** Run `npx vitest run apps/desk/server/app.test.ts -t "SSRF"` → PASS (es un guard ya existente; el test lo fija). `npm test` completo verde. `npm run typecheck` exit 0. `npm run lint` 0 errores. `npm run build` OK.

- [ ] **Step 4: Commit + push a main** (último push directo; deja el workflow existiendo y corriendo una vez para poder marcarlo como required check):
```bash
git add .github/workflows/ci.yml apps/desk/server/app.test.ts
git commit -m "ci: workflow typecheck+lint+test+build + test guard SSRF (F5-01/F5-03)"
git push origin main
```

## Task 2: Branch protection (usuario, en GitHub)

- [ ] **Step 1:** Esperar a que el workflow **CI** corra una vez (pestaña Actions del repo) — así el check `verify` aparece como seleccionable.
- [ ] **Step 2:** GitHub → repo `ambientalia-desk` → **Settings → Branches → Add branch ruleset (o Branch protection rule)** para `main`:
  - ✅ Require a pull request before merging.
  - ✅ Require status checks to pass before merging → seleccionar **CI / verify**.
  - ✅ (opcional) Require branches to be up to date before merging.
  - ✅ (opcional) Do not allow bypassing the above settings (incluir admins).
  - Save.
- [ ] **Step 3:** A partir de aquí, el flujo de trabajo cambia (ver runbook abajo).

## Runbook — nuevo flujo de trabajo (a partir de Fase C)
```bash
git checkout -b fix/lo-que-sea      # rama por cambio
# ... cambios + commits ...
git push -u origin fix/lo-que-sea
gh pr create --fill                  # o abrir PR en la web
# CI corre en el PR → si verde, "Merge" → push a main → EasyPanel despliega código ya validado
```
- Ya **no** se commitea directo a `main` (branch protection lo impedirá).
- EasyPanel sigue desplegando en push a `main`, pero `main` solo recibe merges con CI verde.

## Notas
- `npm test` usa pg-mem → no requiere Postgres en CI.
- `npm run lint` falla solo en *errores* (los 152 warnings `no-explicit-any` no rompen CI; correcto).
- Branch protection no se puede fijar por código del repo; lo configura el usuario (UI o `gh api`).
